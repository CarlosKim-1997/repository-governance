# Optional verification workflow

This guidance and the local helper are optional tooling in Distribution 0.3.0. Governance 1.0.0, its five structured schemas, IDs, manifest and Task lifecycle are unchanged. This is procedural guidance, not new normative authority or a retroactive completion gate. The structural checker remains deterministic, read-only, offline and structural. A helper never changes a Task, ratifies Canon, or establishes semantic acceptance.

## Before implementation

In the Task's **Verification** and **Completion Criteria**, or ordinary Work notes when a Task is unnecessary, record:

1. Requirement source (file/heading or supplied instruction) and bounded scope. Local labels such as `total` are Task-local, not repository-wide IDs.
2. Inputs, expected observations and failure conditions defined before implementation, with the basis for each expectation: a rule, direct calculation, or explicit business condition.
3. Exact executable, argument array, workspace-relative working directory, required permissions, timeout, output cap, and local artifact directory. Review scripts and side effects as well as the command name. A stored command is not authorization.
4. Declared implementation, tests, configuration, rules and lockfiles that bind the observation. Directory targets include every regular file recursively, including future additions; explicit file targets only cover those named files. Add relevant target directories when detecting new files matters. There is no ignore list and no automatic dependency discovery.

After execution, write a Work report with the actual observation, environment, result path, exact inspected artifact scope, mechanical result, semantic acceptance or human review, unverified/blocked reasons, and what must be rerun after later changes. Keep detailed logs in Work or local artifacts, never append them to Current State or AGENTS.md.

## Installed helper

Node 20+ is required only to run the tools. There are no helper runtime dependencies; the consumer need not have Git, npm, or project dependencies. Copy `tooling/governance/verification-plan.example.json` to a project-owned plan, adapt it, and review it before authorizing commands. The sample checks only a direct calculation. The requirement location in the sample must be replaced with the project's actual source.

From the consumer root:

```sh
node tooling/governance/verify.mjs verification-plan.json
node tooling/governance/verify.mjs verification-plan.json --run --approve DISPLAYED_PLAN_SHA256
node tooling/governance/verify.mjs verification-plan.json --check .verification-runs/RUN/result.json
```

The first command prints the plan, command/arguments, cwd, expectations, permissions, target hashes, timeout, per-stream log cap, and artifact directory. It executes no verification commands and writes no artifacts. A valid read-only plan exits 0 while remaining UNVERIFIED. `--run` plus the exact current plan hash is an explicit authorization request by the caller; this does not elevate the caller's permissions. Only run commands already authorized for that project and environment. Do not include destructive operations, live service changes, dependency installation, or external API calls in routine verification.

The format names `verification-plan/local-v1` and `verification-result/local-v1` are non-normative tooling formats. Do not register them in `supported_schemas` or call their validation Governance meaning validation. Every command has `inputs`, `expected`, `basis`, `failure`, `permissions`, a `command` with `executable`, `args`, `cwd`, `timeoutMs` (1..3600000), `maxOutputBytes` (1..1048576 per stream), and `assertions.exitCode: 0`. Human entries use `kind: human` and the same descriptive fields without command settings. `node` selects the running Node executable; other native executables resolve through the inherited PATH, or an explicit absolute executable path. Relative executable paths are relative to the workspace, not cwd. Workspace paths use forward slashes. All symlinks/junctions in target, cwd, plan and artifact paths are rejected, including in-workspace links. Windows `.cmd`, `.bat`, `.ps1` require a shell and are unsupported; use a native executable with arguments. No command string is evaluated and `shell` is false.

## Reading a result

Process outcome, mechanical observation and semantic acceptance are separate. `EXITED` records the actual exit code; `FAILED_TO_START`, `SIGNALED`, `TIMED_OUT`, `INTERRUPTED`, `NOT_RUN` and incomplete observation are distinct. Run/check exit 0 means declared mechanical gates SATISFIED; 1 means blocked, unmet, stale or unverified; 2 means tool failure. No exit code completes a Task.

`stdoutIncludes` and `stderrIncludes` check literal observations. Exit 0 alone remains UNVERIFIED. Test execution counts remain UNKNOWN unless `testSummary: node-tap` is declared and a complete unique summary is observed. The deliberately narrow TAP reader requires positive passing counts, no failures/cancellations/skips/todo, and named cases beyond file-only tests. It supports the current native Node executable (`node` or its absolute path), `--test`, `--test-reporter=tap` (or the equivalent two arguments), an optional `--`, and explicit workspace-local regular test files. Relative file arguments are resolved against command cwd. Top-level observed Subtest names are compared with those actual invocation paths, including extensionless and arbitrary-suffix files; no extension list guesses whether a case ran. Node TAP hash/backslash escapes are decoded for this comparison without trimming meaningful filename whitespace. Unsupported displays and ambiguous control-character escapes remain UNVERIFIED. A name equal to an invocation file remains ambiguous and UNVERIFIED. Automatic discovery, directories, globs and extra runner flags are not understood and remain UNVERIFIED. Genuine named cases, including names ending in a source extension, can satisfy the declared gate. Empty test files, zero tests, all-skipped tests, incomplete or unsupported output never establish satisfaction. Counts and text cannot establish assertion quality or requirement correctness. No universal test parser or language discovery is provided.

SATISFIED describes only declared mechanical conditions. `semanticAcceptance` is always UNVERIFIED; record human acceptance separately with its actual basis. Human entries always remain UNVERIFIED. Missing required fields or an empty plan block execution. Truncated output remains UNVERIFIED even with exit 0. Review exact log observations, not just the label.

The helper hashes the raw plan, its own executable source and the declared file contents before/after execution. `--check` rereads the current plan/files/helper and the retained logs. Source/test/rule/lockfile changes, declared directory file additions/deletions, missing observations or plan edits invalidate reuse. Git HEAD and bounded working-tree status are auxiliary observations; the same HEAD does not imply the same files. Git absence does not prevent hashing. Outputs must be in a dedicated artifact directory disjoint from every target, so new run logs alone do not invalidate source evidence. Ignore that local output directory in your project's source control if appropriate; never use an ignore rule to conceal relevant targets. A failed run can have current hashes and still fail its mechanical gates.

The existing non-normative result format also requires valid result/check start/end timestamps, environment and content bindings. Executed checks record a normalized invocation (`executable`, copied `args`, absolute `cwd`) alongside executable/cwd; `--check` resolves the approved plan with the same rules and compares both. A bare PATH executable is recorded as that bare name, not a claim about all PATH/environment dependencies. Exit/signal/failure/observationMissing/cleanup must be explicit and consistent with the recorded outcome. Each stdout/stderr entry requires integer bytes/retained, exact truncation boolean, SHA-256 and the run-local log path; its retained size/hash must match the actual log. Human and NOT_RUN entries have their own timestamped non-execution shape and cannot carry invented process observations. Complete failed-start, timeout or interruption observations can remain current while BLOCKED; incomplete observations, omitted fields, contradictory calls/times/outcomes or damaged logs return current:false and BLOCKED/UNVERIFIED with reasons. JSON property ordering is irrelevant. These checks detect mistakes/corruption, not malicious forgery. Older incomplete records are not upgraded or backfilled: rerun verification with the current helper. Governance supported_schemas remains unchanged.

## Boundaries and platforms

The helper adds no upload, telemetry, external AI, Git push or Computer Use. Its child processes inherit environment and permissions (except Node's internal `NODE_TEST_CONTEXT`, removed to avoid nested-runner protocol interference). Environment values are not dumped. Commands/arguments, filenames and stdout/stderr can still contain secrets. Review logs and reports before sharing.

Timeout and AbortSignal/CLI SIGINT/SIGTERM request best-effort cleanup. Windows uses native `taskkill /t /f` with a direct-child fallback; Linux/macOS use a process group and SIGKILL. Cleanup itself has a bounded wait; pipes held open after cleanup become an incomplete observation. Truncation drains output while retaining at most the configured bytes per stream. A timeout bounds each command, not filesystem hashing or the total multi-command plan. A killed helper, power loss or failed log write may leave a partial run directory without a final result; that is unusable evidence. Detached descendants, path-swap races, hard links, resources other than time/output, network and filesystem side effects are not isolated. Use environment controls when isolation is required. Platform support is limited to native executables on Windows/Linux/macOS; validate process cleanup and permissions on the intended OS. See the accompanying implementation report for environments actually exercised.

Hashes track changes; they are not signatures or tamper-proof proof. The same worker can edit the helper, test, log and hashes. Before/after hashing misses changes reverted during execution and dependencies outside the declared scope. Revalidate after any material implementation, test, plan, rule, configuration or dependency change, after integration, or when environment assumptions change. A final read-only review plus actual executions is useful but is not independent proof of correctness.

## Work report example

Requirement: `requirements.md`, “total”; scope: CSV total only. Inputs: amounts 5 and -2. Expected: 3, by direct arithmetic. Failure: wrong total, error exit, zero executed tests, or changed target scope. Authorized command: `python` with `["-m", "unittest", "discover", "-s", "tests", "-v"]`, cwd `.`, local fixture/files only. Capture Python version separately; unknown test-count parsing requires review of the unittest summary. Record the exact observed summary and artifact result path, platform/runtime, declared file hashes, mechanical status and human acceptance basis. Recheck source, tests, rules and configuration before reusing the observation. This example defines no new ID or Canon record.
